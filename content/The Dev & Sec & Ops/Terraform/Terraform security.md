> **Terraform security** covers two related concerns: the security of the infrastructure that Terraform creates, which is decided in code before deployment, and the security of the Terraform toolchain itself — state, plans, providers, modules, and the pipelines that run them.

- A Terraform configuration is a program with administrative control over the infrastructure it manages. A misconfiguration in a shared module is replicated into every environment; a compromised pipeline can modify or destroy everything the pipeline can reach.
- In exchange, Terraform makes infrastructure security reviewable, testable, and enforceable before any change reaches a cloud API.
- General IaC security implications are introduced in [[Infrastructure as Code#Security implications of IaC]].

## Threat model

### Assets

| Asset | Why it is sensitive |
| ----- | ------------------- |
| State files | Contain every attribute of every managed resource in plaintext, including secrets; writing state changes what Terraform believes exists. |
| Saved plan files | Contain configuration, variable values, and a state snapshot in plaintext. |
| Variable files and pipeline variables | May contain environment-specific and sensitive inputs. |
| Pipeline runners | Execute Terraform, providers, and any code they load, with the pipeline's privileges. |
| Providers and modules | Third-party code executed with those privileges. |
| The configuration repository | Whoever can change it, or change what the pipeline executes, controls the infrastructure. |

### Attack surface

| Vector | Description |
| ------ | ----------- |
| Insecure infrastructure definitions | Public storage, open security groups, unencrypted disks, wildcard IAM policies deployed by code. |
| Secret exposure | Secrets written to state, plan files, logs, `.tfvars` files, or version control. |
| State exposure | State readable by more principals than necessary, or stored without encryption and versioning. |
| State tampering | Unauthorised writes to state that change what Terraform will create, modify, or delete. |
| Supply chain | Malicious or compromised providers, modules, or Terraform binaries. |
| Code execution during plan | Configuration from untrusted changes executing code on the runner before review. |
| Pipeline abuse | Unreviewed changes applied to production, or over-privileged pipelines. |
| Drift | Manual changes that bypass review and silently weaken controls. |

## Secrets management

### How secrets reach state

- Terraform stores every attribute of every managed resource and data source in state. Any secret that is an argument or attribute of a resource ends up there in plaintext:
	- passwords passed to resources (database master passwords, VM admin passwords);
	- values generated by providers (`random_password`, `tls_private_key`, generated access keys);
	- values read by data sources (secrets manager entries, Vault secrets);
	- computed attributes returned by the platform (storage account access keys, kubeconfigs, connection strings).
- `sensitive = true` on variables and outputs, and provider-side sensitive marking, only redact values in CLI output. They do not remove them from state or plan files.

### Strategies, in order of preference

1. **Let the platform own the secret.** Many managed services generate and rotate credentials themselves and expose only a reference, so the secret never passes through Terraform. Examples: RDS `manage_master_user_password` (stored in AWS Secrets Manager), managed identities and workload identities instead of service account keys, Key Vault-generated keys.
2. **Keep the secret ephemeral.** Ephemeral resources, ephemeral variables, and write-only arguments (Terraform 1.10 and 1.11 and later) pass a secret to a resource without persisting it in plan or state (see [[Terraform resources#Ephemeral resources]] and [[Terraform resources#Write-only arguments]]):

```hcl
ephemeral "random_password" "db" {
  length  = 32
  special = true
}

resource "aws_secretsmanager_secret" "db" {
  name = "orders/db/master"
}

resource "aws_secretsmanager_secret_version" "db" {
  secret_id                = aws_secretsmanager_secret.db.id
  secret_string_wo         = ephemeral.random_password.db.result
  secret_string_wo_version = 1
}

resource "aws_db_instance" "orders" {
  identifier          = "orders"
  engine              = "postgres"
  instance_class      = "db.t4g.medium"
  allocated_storage   = 50
  username            = "app_admin"
  password_wo         = ephemeral.random_password.db.result
  password_wo_version = 1
}
```

3. **Store the secret in a secrets manager and reference it.** Applications read the secret at runtime from AWS Secrets Manager, Azure Key Vault, Google Secret Manager, or HashiCorp Vault; Terraform manages only the container and access policy, not the value.
4. **Accept the secret in state and protect state accordingly.** When none of the above is possible, the protection of the state storage is the protection of the secret (see [[#Protecting state and plan files]]).

### Anti-patterns

| Anti-pattern | Consequence |
| ------------ | ----------- |
| Secret literals in `.tf` files | The secret is committed to version control and copied into every plan file. |
| Secrets in committed `.tfvars` files | Same as above, and easily missed in review. |
| Secret values as default values of variables | The default is part of the code. |
| Secrets in non-sensitive outputs | Printed after every apply into terminal and CI logs. |
| `nonsensitive()` on secrets to silence errors | Removes the redaction that prevents disclosure. |
| Debug logging in shared pipelines | `TF_LOG=DEBUG` and `TRACE` logs include request bodies and redacted values. |

- Repositories should be scanned for committed secrets (for example, with Gitleaks or TruffleHog in pre-commit hooks and CI), and `.gitignore` should exclude state and plan files (see [[Terraform project structure#Version control hygiene]]).

## Protecting state and plan files

- **Never commit state** — `*.tfstate` and `*.tfstate.*` must be excluded from version control in every repository.
- **Use a remote backend with encryption, versioning, and restricted access** (see [[Terraform backends#Securing state storage]]).
- **Scope state access narrowly** — one state per configuration and environment, each readable and writable only by the identities that plan and apply that configuration. Avoid designs in which many consumers need read access to a state (see [[Terraform backends#Sharing state between configurations]]).
- **Separate environments at the storage level** — production state should not live in the same bucket, container, or workspace set as development state, because CLI workspaces share access controls (see [[Terraform state#Workspaces]]).
- **Audit state access** — enable data-access logging on the state storage and alert on access by unexpected principals.
- **Protect state writes as carefully as reads** — whoever can write state can make Terraform believe resources exist or do not exist, which changes what the next apply creates or destroys. Only the apply identity should hold write access; backend versioning allows tampering to be detected and reverted.
- **Treat plan files as secrets** — store them only as short-lived, access-controlled pipeline artifacts, never attach them to pull requests, and delete them after apply. Rendered plan text posted to pull requests should be generated with secrets redacted (which `terraform show` does for sensitive values) and reviewed for non-marked secrets.
- **Consider client-side encryption** — OpenTofu can encrypt state and plan files before they reach storage.

## Supply chain security

Terraform executes three kinds of external code: the Terraform binary, providers, and modules (which can contain provisioners and data sources that run programs).

### Terraform binary

- Install from official packages or verify release signatures and checksums (see [[Terraform#Verifying release binaries]]).
- Pin the CLI version in pipelines and with `required_version`, and use the same version everywhere.

### Providers

- **Declare every provider explicitly** with `source` and a version constraint, to avoid implicit resolution to an unintended `hashicorp/<NAME>` address (see [[Terraform providers#Implicit provider resolution]]).
- **Commit the dependency lock file** and run CI with `terraform init -lockfile=readonly`, so that a provider or version not previously reviewed cannot be installed silently. Changes to `.terraform.lock.hcl` should be reviewed like code changes.
- **Record hashes for all platforms** with `terraform providers lock`, so that checksum verification works on every runner.
- **Prefer official and well-established providers**, and evaluate community providers before adoption: publisher identity, maintenance activity, source code availability, and the permissions the provider needs.
- **Control installation centrally** where required: a network or filesystem mirror containing only approved providers, combined with a `provider_installation` block that excludes direct downloads (see [[Terraform providers#Provider installation]]).
- Terraform verifies the signature of providers downloaded from a registry against the publisher's registered key. This proves the package came from the namespace owner; it does not prove the code is benign.

### Modules

- Module versions are not recorded in the lock file. The version pin in the `module` block is the only control.
- **Pin registry modules to exact versions** in production root modules, and upgrade deliberately.
- **Pin Git modules to full commit SHAs** rather than tags or branches, because tags can be moved.
- **Review third-party modules** before use, with attention to provisioners, `external` and `http` data sources, `local_file` resources, and the providers they require.
- **Vendor or mirror critical modules** into an internal registry or repository, so that an upstream deletion or compromise does not affect deployments.
- Dependency update tools (Renovate, Dependabot) can propose provider and module upgrades as pull requests, which keeps versions current while preserving review.

## Code execution during plan

- `terraform plan` is not a read-only operation from the runner's perspective. During planning, Terraform:
	- downloads and executes provider plugins named in the configuration and the lock file;
	- downloads modules from the sources named in the configuration;
	- executes `external` data sources and performs `http` data source requests (see [[Terraform data sources#Special-purpose data sources]]);
	- reads local files through filesystem functions.
- Provisioners do not run during plan, but everything above does.
- Consequently, planning a change is equivalent to executing it on the runner with the runner's privileges and network access. A pipeline that automatically plans every pull request runs code supplied by whoever opened the pull request.

Controls:

- Do not run automatic plans with production privileges for changes from untrusted contributors (for example, pull requests from forks). Require a maintainer to approve the run first.
- Give planning jobs the least privilege that planning needs, separate from apply jobs, and keep apply privileges behind branch protection and manual approval.
- Run Terraform on ephemeral, isolated runners with restricted network egress, so that code executed during plan cannot persist or reach unrelated systems.
- Use `-lockfile=readonly` and a controlled provider installation configuration, so that planning cannot introduce unreviewed providers.
- Flag `external` data sources, `local-exec` provisioners, and new provider sources in code review, or block them with policy for untrusted repositories.

## Static analysis

Static analysis tools scan Terraform code (or plans) for insecure configurations before deployment: unencrypted storage, public network exposure, permissive IAM policies, missing logging, disabled versioning.

| Tool | Description |
| ---- | ----------- |
| Checkov | Policy-based scanner by Prisma Cloud with a large built-in rule set; scans HCL and plan JSON, supports custom policies in Python or YAML. |
| Trivy | Aqua Security's multi-purpose scanner; its `config` mode includes the former tfsec engine and rules. |
| KICS | Checkmarx's scanner with Rego-based queries for many IaC formats. |
| TFLint | Linter with provider rulesets; primarily correctness, with some security-relevant rules (see [[Terraform testing#Static checks]]). |
| Semgrep | General code scanner with community Terraform rules and custom pattern support. |

- Scan a directory with Checkov:

```bash
checkov -d .
```

- Scan a plan instead of the source, which resolves variables, modules, and computed values that static HCL analysis cannot see:

```bash
terraform show -json tfplan > tfplan.json
checkov -f tfplan.json --framework terraform_plan
```

- Scan a directory with Trivy:

```bash
trivy config --severity HIGH,CRITICAL .
```

- Scan with KICS from its container image:

```bash
docker run --rm -v "$(pwd)":/src checkmarx/kics scan -p /src -o /src/kics-results
```

- Export findings as SARIF for code scanning dashboards such as GitHub code scanning:

```bash
checkov -d . -o sarif --output-file-path results/
trivy config --format sarif --output trivy.sarif .
```

### Suppressions

Every scanner produces findings that are intentional for a specific resource. Suppressions should be inline, specific to one rule, and justified:

```hcl
resource "aws_s3_bucket" "public_assets" {
  # checkov:skip=CKV_AWS_18: Access logging is centralised through CloudFront logs.
  # trivy:ignore:AVD-AWS-0089
  bucket = "acme-public-assets"
}
```

- A suppression without a reason, or a global suppression of a rule in a configuration file, hides future violations. Suppressions should be reviewed like code.

## Policy as code

> **Policy as code** expresses organisational rules — allowed regions, required tags, mandatory encryption, forbidden resource types — as executable policies that are evaluated against every plan before apply.

Policies are evaluated against the JSON plan, which contains the fully resolved values of every planned resource (`resource_changes[].change.after`). This makes them more precise than source-code scanning.

### Open Policy Agent and Conftest

- Write a policy in Rego:

```rego
# policy/terraform.rego
package main

import rego.v1

deny contains msg if {
	rc := input.resource_changes[_]
	rc.type == "aws_vpc_security_group_ingress_rule"
	some action in rc.change.actions
	action in {"create", "update"}
	rc.change.after.cidr_ipv4 == "0.0.0.0/0"
	rc.change.after.from_port <= 22
	rc.change.after.to_port >= 22
	msg := sprintf("%s allows SSH from the internet", [rc.address])
}

deny contains msg if {
	rc := input.resource_changes[_]
	rc.mode == "managed"
	some action in rc.change.actions
	action == "create"
	tags := object.get(rc.change.after, "tags_all", {})
	not tags.Owner
	msg := sprintf("%s is missing the Owner tag", [rc.address])
}
```

- Evaluate a plan against the policies:

```bash
terraform plan -out=tfplan
terraform show -json tfplan > tfplan.json
conftest test tfplan.json --policy policy/
```

- Conftest exits with a non-zero status when any `deny` rule produces a message, which fails the pipeline before apply.
- Resources that do not support tags have no `tags_all` attribute; a production policy restricts tag rules to taggable resource types.

### Sentinel

- Sentinel is HashiCorp's policy language, evaluated by HCP Terraform and Terraform Enterprise between plan and apply:

```text
import "tfplan/v2" as tfplan

allowed_types = ["t3.micro", "t3.small", "t3.medium"]

instances = filter tfplan.resource_changes as _, rc {
	rc.type is "aws_instance" and
	rc.mode is "managed" and
	(rc.change.actions contains "create" or rc.change.actions contains "update")
}

main = rule {
	all instances as _, rc {
		rc.change.after.instance_type in allowed_types
	}
}
```

- The `tfplan/v2` import exposes the planned changes; `tfconfig/v2` exposes the configuration (for example, provider settings) and `tfstate/v2` the prior state.

- Policies are grouped into policy sets attached to workspaces or projects, with an enforcement level per policy:

| Level | Behaviour |
| ----- | --------- |
| Advisory | Report the failure and allow the run to continue. |
| Soft mandatory | Block the run unless an authorised user overrides the failure. |
| Hard mandatory | Block the run with no override. |

- HCP Terraform also accepts OPA policies, with advisory and mandatory enforcement levels.

### Choosing where to enforce

- **Pre-commit and pull request** — scanners and Conftest give developers fast feedback.
- **Between plan and apply** — policy evaluation on the actual plan is the authoritative gate, because it sees resolved values.
- **In the cloud platform** — service control policies, Azure Policy, and organisation policies enforce the most critical rules (allowed regions, no public storage) regardless of how a change is made, including changes outside Terraform. Terraform policies complement but do not replace them.

## Auditing and drift detection

- **Attribute changes to Terraform** — give the identities used by Terraform distinctive names and session names, so that cloud audit logs (AWS CloudTrail, Azure Activity Log, Google Cloud Audit Logs) show which changes were made by which pipeline and which were made by humans.
- **Tag managed resources** with the repository and configuration that manage them (for example, through `default_tags`), so that incident responders can find the code that owns a resource.
- **Keep pipeline run history** — the plan output, the approver, the commit, and the apply log of every production change form the change record of the infrastructure.
- **Detect drift on a schedule** — a periodic `terraform plan -detailed-exitcode` in each production configuration reports changes made outside Terraform (see [[Terraform automation#Scheduled drift detection]]). Drift in security-relevant resources (IAM, network rules, encryption settings) should raise an alert, not just a report.
- **Monitor the infrastructure Terraform creates** — Terraform can provision the monitoring itself: log groups, alarms, diagnostic settings, and security service configuration (for example, CloudWatch alarms, Azure Monitor diagnostic settings), which makes observability part of every environment by default.

## Hardening checklist

**Code**

- Every provider declared with `source` and a version constraint; lock file committed.
- Registry modules pinned to exact versions and Git modules to commit SHAs in production.
- No secrets in `.tf`, `.tfvars`, or variable defaults; secrets handled by the platform, ephemeral values, or a secrets manager.
- Reusable modules secure by default; insecure options explicit and named as such.
- `prevent_destroy` on stateful and security-critical resources.
- Scanners and policy checks in pre-commit and CI, with justified inline suppressions only.

**State and plans**

- Remote backend with encryption, versioning, locking, TLS-only access, and no public access.
- Separate state, and separate storage access, per environment and per configuration.
- State and plan files excluded from version control; plan artifacts short-lived and access-controlled.
- Data-access logging on state storage.

**Pipelines**

- Plan and apply run only in CI, on ephemeral runners, with the Terraform version pinned.
- Separate, least-privilege identities for plan and apply; apply gated by branch protection and approval.
- No automatic privileged plans for untrusted contributions.
- `terraform init -lockfile=readonly` and controlled provider installation.
- Debug logging disabled by default; logs reviewed for secret exposure.

**Operations**

- Scheduled drift detection with alerts for security-relevant drift.
- Manual production changes restricted to a documented break-glass procedure, followed by codification.
- Cloud-level guardrails (organisation policies) for the most critical rules.
